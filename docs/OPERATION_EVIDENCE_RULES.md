# Operation–evidence mapping

This is a rebuildable diagnostic projection, not an authority or promotion
record. Cognitive Gym remains a first-party plugin candidate; the operational
projection is a core diagnostic consumer. No routes or plugin mounts change.

## Sources and identifiers

The catalog reads the explicitly headed capability handoff table and named
safe-frontier promotions in `CONTINUATION_CHECKPOINT.md`. A later explicit
promotion overrides the earlier NOT READY entry only for that named operation.
The top current-frontier section outranks retained historical sections. Shipped
work establishes reachability, not permission to train. Each assertion retains
the source path, exact byte hash, excerpt, scope and source-priority explanation.

Operation IDs use the handoff capability name, normalized to `op.<slug>`.
Renaming an authoritative operation requires an explicit adapter migration;
it must not silently combine earlier IDs. Named kernel/contract implementation
bindings additionally expose source ingestion, governed finding, Helix and
stated-datum corroboration. File existence alone never grants stable status.
Behavioral suboperations append page-selection, supported-claim-limits and
unknown-versus-false to the corresponding stable interface ID. C11 binds to
the supersession reader only when the evidence identifies `spin_current_sources`.
These are explicit source adapters, not a second capability ontology.
The shipped name "Datum corroboration boundary" explicitly joins the
`op.datum-corroboration` implementation binding; it does not imply a generic
cross-source relationship capability. Both source references are retained.

Unknown or conflicting capability/actor attribution in the accepted normalized
projection remains unresolved. Only explicit GO encounters join the operational
GO track. GOtex, teaching, preliminary abstract exercises and evaluator records
are not pooled into operational readiness. Source hashes are rechecked before
reading material or results. All historical records remain in the original feed.
An untested broad interface is not a claim that its mapped suboperation has no
observations. Child evidence does not automatically establish the full interface.
The first applied C01 result records requested-page alignment, but its normalized
model/instrument fields remain unresolved. Its content is preserved without
counting it as a usable control; the other mapped positives stand separately.

## Application states

| State | Required evidence |
|---|---|
| STABLE | Explicit stable handoff within scope, or all implementation, tests, applicable deployment, relevant corpus proof and no invalidating blocker explicitly established |
| REACHABLE | Explicit invocable/shipped workflow; stable proof incomplete |
| EXPERIMENTAL | Implementation evidenced; reachability/stability incomplete |
| UNAVAILABLE | Explicit absence within a retained implementation search scope |
| UNRESOLVED | Missing or conflicting evidence; absence of a discovered file is insufficient |

An invalidating blocker prevents STABLE. Commit presence and successful tests
alone do not grant trainability. The latest active Claude frontier and stable
handoff frontier are separate fields. Newer shipped sheet-identity, callout and
orientation work does not inherit the older safe-set authorization.

## GO readiness

UNTESTED means no attributable operational observation in this mapped scope.
DEVELOPING means observations exist, including invalid/unscored observations;
it does not assert success. Usable positives require an aligned response,
contract compliance, delivery/material validity and an identified model baseline.
Mixed model baselines are unresolved rather than pooled.

CONDITIONALLY READY and RELIABLE FOR THIS OPERATION require explicit authorized
operational acceptance identifying the same operation, scope, model and evidence,
plus usable positive observations and the scoped negative-control requirement.
The projection does not manufacture that acceptance or certification. No current
reader supplies such acceptance from stage closure, pass counts or Gym status.
The higher categories are testable rule branches, not claims about current GO.

## Negative-control scope

Page-based selection needs absent-target withholding; supported-claim limits
and unknown-versus-false need unsupported/null conditions; currentness reading
needs stale/unresolved or candidate-lineage restraint. Existing developmental
records contain these controls and justify requiring them for these four scopes.
Other operations do not automatically inherit universal restraint tests.
NOT_REQUIRED needs a scope reference. Missing requirements do not imply a pass.

Keep valid negative misses, invalid/unscored output and aligned negatives
separate. A later pass does not erase an earlier miss in the same mapped series.
Until a separately scoped acceptance resolves applicability, the projection is
conservative. C11 malformed model JSON is not itself an instrument defect.
Task content, contract compliance, instrument validity and application defects
remain separate in the attached observations. Strict parsing is unchanged.

## Shared state, owner and band

Rules run in this order after conflict/unknown-identity rejection:

1. Explicit invalid instrument: BLOCKED_BY_INSTRUMENT, CODEX, BLOCKED.
2. An explicit authority blocker, or ready behavior with unresolved/denied
   authority: BLOCKED_BY_GOVERNANCE, GOVERNANCE (PRODUCT_OWNER when explicitly
   pending that decision), BLOCKED.
3. Positive behavior plus unsatisfied required negative control:
   BLOCKED_BY_NEGATIVE_CONTROL. CODEX if application stable; otherwise
   SHARED / MULTIPLE. FRAGILE for a valid miss; BLOCKED for absent/unscored proof.
4. Explicitly non-trainable application path: IMMATURE, with the source-recorded
   dependency owner. A stable component alone cannot enter shared operational use.
5. Stable application, accepted GO readiness and permitted scoped use:
   SHARED_FRONTIER. No outstanding gap owner is invented.
6. Stable application without that readiness: APPLICATION_AHEAD, CODEX.
7. Accepted GO readiness with unavailable/experimental/reachable application:
   GO_AHEAD, CLAUDE.
8. Both application and GO development incomplete: IMMATURE, SHARED / MULTIPLE.
9. Insufficient application evidence: UNRESOLVED.

UNTESTED band denotes no mapped GO encounters where the application state is
known. UNRESOLVED covers insufficient band evidence. EXCELLENT, GOOD, ADEQUATE
and POOR remain reserved: no approved comparative rubric supports them. Every
row explains WHY THIS BAND and retains its evidence. Bands do not replace states.
No numeric threshold, average, intelligence score or minimum calculation exists.

Conflicting assertions produce UNRESOLVED with both references and the reason;
they are not resolved by voting. Current-vs-history source priority is explicit.
Application defects are preserved as their own observation field, not scored as
cognitive failure. An invalid instrument blocks use independently of task content.

## Snapshot and gate

`tools/export_cognitive_gym.py --source <evaluator> --output <file> --frontier`
exports the optional operational view. Without the flag, legacy output is
unchanged. Neither path publishes production automatically or mutates history.

Each capability contains capability_id, capability_name, application_state,
go_state, shared_state, gap_owner, qualitative_band, why_this_band,
latest_evidence, positive_control_state, negative_control_state,
negative_control_findings, governance_state, unresolved_reasons,
last_verified_at, safe_for_training, model_baseline, observations, scope and
source_priority. `last_verified_at` is a recorded evidence timestamp, not a
claim that deployment was reverified now. Missing timestamps stay UNRESOLVED.
The export receipt separately gives capture time and serialized hash; the
payload includes a canonical content hash and normalized-input hash.

The UI remains gated when an operational application/shared state or current
frontier is unresolved. A known blocked state can be displayed honestly;
an uncertain operation boundary cannot become a confident gauge.

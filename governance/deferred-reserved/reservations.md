# Deferred / Reserved — Acknowledged, Not Designed

**Reserved ≠ authorized for implementation.** Every item below is a real, named gap this baseline deliberately stops short of designing, because designing it now would be premature relative to the much smaller currently-authorized implementation tranche (see `STATUS.md`). Naming a gap here is not a roadmap commitment and not a design.

1. **Machine Model / Installed Asset Identity.** No first-class, identity-bearing representation of a physical installed object surviving across many drawing/maintenance-record revisions. Load-bearing for long-term P3/O&M continuity specifically, not just a vague future nicety — confirmed by tracing the full Requirement→Handback chain and finding this the one point nothing in the current model represents. `Finding`+`Artifact` can carry "which specific asset" as descriptive content in the meantime.
2. **Infrastructure / tenant hosting isolation.** Separate encryption keys, separate physical/cloud tenancy, deployment-level separation. Everything resolved in this baseline is data-model and application-layer; this is a distinct, unsolved operational-security layer, out of scope for this architecture review.
3. **Recurring `TemporalObligation` implementation.** Current shape models one due-date, not a repeating series. Precise fix already specified: a recurrence descriptor generating individually-governed occurrence records, matching the non-destructive, one-record-per-occurrence discipline used everywhere else — not a single mutable "next due date" field.
4. **Experience Corpus partition/promotion mechanics.** The shape is resolved (see `specified-unbuilt/cross-boundary-architecture.md`'s confidentiality pipeline); the detailed eligibility rules, re-identification-check implementation, and delay/release timing are not.
5. **Multi-decade storage strategy.** Flat-JSON-per-project has never been stress-tested against decades of accumulated `TemporalObligation` instances, performance history, and lifecycle interventions for a long-running P3 project.
6. **Template-library staleness governance.** No periodic review process exists yet for keeping Contract-DNA template sets current — a real risk (a stale template systemically biases what gets instantiated on every project using it) named but not solved.
7. **Detailed workspace-module/application-surface structure.** Option C (shared kernel-integration shell, genuinely distinct workspace-type modules per Perspective) was chosen over separate full applications and a single configured application — the exact module boundaries are not specified.
8. **A future governed legal/dispute context.** Formal contract termination, repudiation/default, insolvency, negotiated termination, and court/arbitral intervention sit structurally outside the ordinary recovery-scenario/`ViabilityAssessment` pipeline (constitutional invariant 17). This baseline only establishes the boundary rule — that such states may never be produced by severity or accumulation within the ordinary pipeline, and must instead be grounded in an actual external legal/contractual event referenced by an authorized human/legal actor. The dedicated record types, authority model, and relationship to `Cancel/Close` for this context are not designed here.
9. **Template-driven omission risk.** A Contract-DNA template set that never prompts for a real obligation can function as a silent ceiling on what gets checked. No dedicated fix beyond the general "full kernel access must remain available beyond whatever a template suggests" discipline and item 6's template-governance review — named as a distinct failure mode from a template asserting a wrong value, not solved separately.
10. **Bulk-import tooling boundary.** Proposed to reduce cross-project isolation friction (see constitutional invariant 8's cost/benefit discussion) — its candidate list must be constructed from the visibility-respecting query, never an unrestricted dump of a source project's private content. A specific implementation caution for whenever this tool is built, not yet built.
11. **Template-authoring discipline.** A human curator could accidentally hardcode project-specific confidential values into a Domain-2b template meant to be generic. A practice/discipline risk, not a structural one — analogous to any shared-document review process, not fixable by architecture alone.
12. **Scenario volume management.** Over a long project life, many accumulated non-adopted Scenarios could become hard to navigate in practice. A usability concern, not an architectural one — the data model itself stays safe regardless.

### `Finding` — implemented
`case_workspace.py:822`. Answers: what discrepancy/observation has a machine or human asserted. `claim_status` defaults to `provisional` — the object is weak-by-default, unlike `Requirement`, by design (this asymmetry is why Requirement branching needed a `"proposed"` status extension and Finding did not — see `specified-unbuilt/investigation-lifecycle-extensions.md`).

### `Relationship` — implemented, one known consistency gap
`case_workspace.py:1105`. Answers: how are two objects connected (open-world `relationship_type`: supports/contradicts/qualifies/references/depicts/corresponds_to/implements/depends_on/blocks/affects/resulted_in/**derived_from**). `provisional`/`confirmed_by` correctly separate machine-asserted from human-confirmed status at the field level — but `confirm_relationship` (`~3776`) mutates these fields **in place** rather than following the append-only/successor pattern used everywhere else in this model. This is a real, honestly-preserved inconsistency: at any single point in time the object's status is still correctly readable, but the pre-confirmation state is not separately reconstructable the way `Finding`→`ReviewerValidation` preserves its full history. Flagged, not yet fixed. **`RELATIONSHIP_TYPE_DERIVED_FROM` (Case-lineage tranche) is a deliberate exception to "provisional by default"** — `derive_case_from_archive` creates it with `provisional=False` directly, since it records a structural fact the method itself establishes at write time, not a machine claim awaiting later human confirmation; see the "Case Archive → Derived Active Case" entry below.

### `Case` / `CaseRecord` — implemented; visibility (Private/Shared/Collaborative) and status (Open/Archived) both implemented as two orthogonal axes, remaining lifecycle extensions unbuilt
`case_workspace.py:1550`. Answers: what investigation is this. **Two separate axes, confirmed and kept separate rather than conflated — this is the architectural correction made during the Archive tranche:** `visibility` (`CASE_VISIBILITY_PRIVATE`/`CASE_VISIBILITY_SHARED`/`CASE_VISIBILITY_COLLABORATIVE`) answers *who can see/participate*; `status` (`CASE_STATUS_OPEN`/`CASE_STATUS_ARCHIVED`, using the field's own pre-existing name — previously present since before this tranche sequence but unenforced/decorative) answers *whether the Case is still alive and mutable*. A Case can validly be, e.g., PRIVATE+ARCHIVED or COLLABORATIVE+ARCHIVED — ARCHIVED was deliberately **not** added as a fourth `visibility` value, since that would have conflated two questions a single enum can't cleanly answer. `created_by`/`shared_by`/`shared_at`/`collaboration_established_by`/`collaboration_established_at`/`collaboration_contribution_type`/`collaboration_contribution_id`/`retracted_by`/`retracted_at`/`archived_by`/`archived_at`/`archive_authority`/`archive_prior_visibility`/`derived_from_case_id` are all implemented. The remaining designed extension set (`CaseLock`, publication anchors) is still specified but unbuilt — see `specified-unbuilt/investigation-lifecycle-extensions.md`.

### Case-scoped route authorization hardening — implemented (route-layer tranche, no domain-model change)
`routes/workspace.py`: every Case-scoped write/download route now derives the *authoritative* Case server-side and rejects (404) if the requester's own `visible_cases_for` doesn't include it, via the shared `_require_visible_case(store, workspace, case_id)` helper — reused, not duplicated, across every route below; no parallel authorization framework was introduced. For routes keyed by an object id rather than a bare `case_id` path segment, the object's *own* recorded `case_id` is looked up server-side first (`_finding_case_id`, `_thread_case_id`, `_rfi_draft_case_id`) — a client-supplied hidden `case_id` form field is never trusted for the authorization decision, only ever used (where still present at all) for redirect/log cosmetics. Routes hardened this tranche: `add_drawing_source`, `post_message`, `validate_finding`, `set_disposition`, `promote_requirement_item_route`, `apply_findings`, `cancel_rfi_intent`, `preview_rfi_draft`, `create_rfi_draft` (checks **both** the URL's `case_id` and the submitted `finding_id`'s own real Case — a visible Case in the URL must not become cover for drafting an RFI against a Finding that actually belongs to a different, private Case), `update_rfi_question`, `issue_rfi_draft`. `create_thread`/`add_thread_message`/`request_thread_attention`/`resolve_thread`/`reopen_thread` (Human Discussion UI tranche) and `artifact_image`/the `preview_finding_id` path in `show_workspace` (Case-visibility tranche) already had equivalent guards before this tranche.

**Deliberately not touched, by design, not oversight:** `share_case`/`retract_case`/`archive_case`/`derive_case`/`adopt_finding`/`adopt_review_message` already enforce their own owner-or-admin authority inside the store layer — a strictly *stronger* check than mere visibility, so adding a visibility pre-check there would be redundant, not protective. `adjudicate_requirement` was inspected and left unchanged: `Requirement` has no `case_id` of its own (project-scoped, not Case-scoped — see the `Requirement`/`Case` entries above), so there is no Case to derive or check; its `case_id` form field is cosmetic (redirect target only). `revise_source` was inspected and left unchanged: a `Source` is not Case-private in this model (the Sources list already renders unconditionally, unfiltered by `visible_cases_for`), and revising one can affect multiple Cases at once (`register_source_revision` returns one notice per affected Case) — there is no single Case to check visibility against. Project isolation was confirmed structural, not requiring a new check: each project's `CaseWorkspaceStore`/`RequirementsRegistry` state lives in its own file, so an id from Project A is simply absent from Project B's `workspace` and fails the store layer's own existing not-found check.

Domain-layer authority checks are unchanged and unweakened by this tranche — route hardening only ensures the *correct* Case reaches those checks (e.g. `_require_case_not_archived`), never substitutes for them. Tests: `tests/test_route_authorization_hardening.py` (14 tests: case-id URL/form spoofing, object-id-from-a-different-Case laundering via a legitimate-looking URL `case_id`, cross-project id reuse, continued SHARED-Case collaboration, and archived-Case write rejection — all via real HTTP requests with genuinely separate authenticated sessions).

**Amendment (per-Finding RFI export tranche):** while wiring the new `export_rfi_draft` route, found `update_rfi_question`'s mutation was inlined directly in the route (`draft["question_text"] = ...; store.save(workspace)`), bypassing the store layer entirely — the one `RFIDraft` write path that never called `_require_case_not_archived`, unlike `issue_rfi_draft` which already did. Fixed by adding `CaseWorkspaceStore.update_rfi_draft_question` (same guard, same single-save pattern as every other governed write) and updating the route to call it instead of mutating the dict directly.

### Collaboration threshold + pre-collaboration retraction — implemented (Constitutional Invariant 12 tranche)
`case_workspace.py`: `CASE_VISIBILITY_COLLABORATIVE` constant, added alongside Private/Shared. `CaseWorkspaceStore._cross_collaboration_threshold_if_qualifying` is the single enforcement point — mutates a Case's visibility to Collaborative in memory only when (a) the Case is currently Shared, (b) the acting actor is non-empty and not the recorded owner; the caller's own subsequent `save()` commits this atomically alongside the qualifying write itself, so a write can never succeed while the transition silently fails or vice versa. Invoked from exactly six call sites, each with its own human-vs-machine origin filter applied *before* calling it: `record_reviewer_validation` and `record_disposition` (both inherently human by construction, no separate origin field needed), `add_review_message` (only `origin == MESSAGE_ORIGIN_HUMAN` qualifies), `request_attention` (no machine analogue exists in this codebase), `confirm_relationship` (uses `confirmed_by`, not `created_by`/creation — a `Relationship`'s `created_by` has no structural guarantee of being human, but confirmation, i.e. `provisional: True → False`, is unambiguously a human act, resolved against every Case referencing the relationship's `from_id`/`to_id` via a new `_cases_referencing_object` helper, since `Relationship` carries no `case_id` of its own), and `record_analysis` (only `trigger.trigger_type == ANALYSIS_TRIGGER_USER_INITIATED` qualifies — `AGENT_INITIATED`/`CLOCK_INITIATED`/etc. never do, regardless of what `triggered_by_actor` holds). **Two deliberate, documented exclusions, not silent omissions:** `Activity` (no origin field exists to distinguish machine- from human-authored, and it has zero real callers anywhere in this codebase to establish a convention either way — see `record_activity`'s own docstring); `RequirementAdjudication` (the ratified spec's own previously-flagged boundary case, now resolved explicitly — adjudicating a Requirement is a contribution to the Requirement's own governed record, a different object from the Case whose evidence it cites, even when that evidence is referenced — see `record_requirement_adjudication`'s own docstring).

`CaseWorkspaceStore.retract_case_to_private` implements the one Shared→Private path: owner-only, rejects outright (before touching any state) once the Case is Collaborative — Constitutional Invariant 12 is enforced at this single validation gate, not merely documented. Does not clear `shared_by`/`shared_at` on retraction — the historic fact of having been shared remains on the record. Route wiring: `share_case`/`retract_case` at `POST /projects/<project_id>/workspace/cases/<case_id>/share` and `.../retract`; the `case_workspace.html` case list shows a Share button for owned Private Cases and a Retract button for owned Shared (not-yet-Collaborative) Cases. `record_reviewer_validation`/`record_disposition`/`confirm_relationship`/`record_analysis` all gained an optional `governance_log` parameter as part of this tranche (backward-compatible, previously absent on the first two) so a `case_became_collaborative` event can be logged uniformly regardless of which of the six paths triggers it. Tests: `tests/test_case_collaboration.py` (26 tests).

### Case Archive — implemented (terminal/frozen lifecycle status tranche)
`case_workspace.py`: `CASE_STATUS_OPEN`/`CASE_STATUS_ARCHIVED` constants, added immediately after `KNOWN_CASE_VISIBILITY_STATES`, reusing `CaseRecord`'s own pre-existing `status` field rather than introducing a new one or extending `visibility` — see the `Case`/`CaseRecord` entry above for the two-axis rationale. `CaseWorkspaceStore.archive_case` performs the one-way OPEN→ARCHIVED transition: rejects a case that's already archived or doesn't exist; authority is owner-only (`actor == case["created_by"]`) **or** an actor whose `actor_role` equals the system's existing `models.ROLE_ADMIN` value (`"admin"`, passed through as a plain string — this domain module still does not import `models`/`services.auth`, preserving its existing framework-decoupling) — no new role architecture was introduced, the admin-override path exists specifically so an unavailable/former owner never permanently locks a Case. Permitted uniformly from PRIVATE, SHARED, or COLLABORATIVE — `visibility` is recorded into `archive_prior_visibility` and left completely untouched by archiving itself (archive never publishes, never privatizes). Records `archived_by`/`archived_at`/`archive_authority` on the `CaseRecord` and logs a `case_archived` `GovernanceLog` event in the same single `save()` call — atomic, no partial states on failure.

**Centralized frozen-state enforcement:** one helper, `CaseWorkspaceStore._require_case_not_archived(workspace, case_id)`, called explicitly at the top of every identified Case-mutating write path rather than scattered/cosmetic per-route checks — currently wired into `attach_source_to_case`, `add_message`, `record_analysis` (case-scoped branch only), `record_reviewer_validation`, `record_disposition`, `add_review_message`, `request_attention`, `confirm_relationship` (checked against every Case referencing either end of the Relationship, via the existing `_cases_referencing_object` helper), `record_activity`, `apply_findings`, `create_rfi_draft`, `issue_rfi_draft`, `share_case`, `retract_case_to_private`, and — added during the Human Discussion UI tranche, once those methods gained real route/UI callers for the first time — `set_review_thread_status`, `resolve_review_thread`, `reopen_review_thread`, and `respond_to_attention` (resolved via the responding `Attention`'s own thread lookup) — i.e. both content-mutation paths and the Case's own visibility-transition paths, including every ReviewThread lifecycle transition, are frozen once archived. `case_id=None` is a legitimate no-op (a Project-level write with no Case at all); a missing Case is left to the caller's own existing existence check.

Archiving is content-preserving, not content-resolving: no method requires resolving open `ReviewThread`s, and no code path rewrites an unresolved item as resolved as a side effect of archiving — unresolved comments, their authorship, and their unresolved state all survive archival completely unchanged, and archiving never depends on the original contributing actor being available or participating again. Route wiring: `routes/workspace.py`'s `archive_case` (`POST /projects/<project_id>/workspace/cases/<case_id>/archive`), passing the real session role through so the store-layer owner-or-admin check can recognize an admin override without the route inventing separate authorization logic. `case_workspace.html`'s case list shows an Archive button (owned or admin-role) only while `case.status != 'archived'`, and the pre-existing Share/Retract buttons now also hide once archived. Tests: `tests/test_case_archive.py` (29 tests).

### Case Archive → Derived Active Case — implemented (Case-lineage tranche)
`case_workspace.py`: `CaseWorkspaceStore.derive_case_from_archive` is the one authorized path forward after archival — "Archive is terminal for the object, not for the work." Source must currently be `CASE_STATUS_ARCHIVED` (rejects an active/open source outright — general Copy/Adopt of an active Case is out of this tranche's scope); authority is the same owner-or-admin pattern as `archive_case` (no new role architecture). Creates a brand-new `CaseRecord` (new id, `created_by`/`created_at` set to the deriving actor/time, `status=CASE_STATUS_OPEN`, `visibility=CASE_VISIBILITY_PRIVATE` unconditionally) and a `Relationship` (`from_type`/`to_type=OBJECT_KIND_CASE`, `from_id`=new Case, `to_id`=archived Case, `relationship_type=RELATIONSHIP_TYPE_DERIVED_FROM`, `provisional=False`) in exactly one `self.save(workspace)` call — atomic, no partial states on failure. Never mutates the archived Case's own record in any way (read-only access to it throughout).

**Working context copied, history referenced, never cloned** — the tranche's own governing rule, implemented literally: `title`/`objective` (overridable via optional `title=`/`objective=` parameters, defaulting to the archived Case's own values) and `source_ids` (a plain list copy — this duplicates a reference list, never the referenced `Source` documents themselves) are the only fields carried onto the new Case. `conversation`/`analysis_ids`/`finding_ids`/`artifact_ids`/`activity_ids` all start empty on the new Case — every historical contribution (review threads/messages, Findings, `ReviewerValidation`, `Disposition`, `Attention`, analysis records, collaboration/archive events) remains attached exclusively to the archived Case, reachable only by following the lineage pointer back to it, never duplicated.

**Lineage, structural and queryable in both directions, deliberately distinct from Supersession/Sharing/Copying:** forward (`derived Case → archived source`) via the new `CaseRecord.derived_from_case_id` denormalized field (cheap direct read) plus the authoritative `Relationship` record (same denormalized-pointer-plus-governed-record pattern already used for `Source.supersedes_source_id`/`Supersession` and `shared_by`/`shared_at`/`GovernanceLog`); reverse (`archived source → every Case derived from it`, one-to-many, no uniqueness constraint) via the new `CaseWorkspaceStore.derived_cases_of(workspace, archived_case_id)`, a filter over `derived_from_case_id`. `RELATIONSHIP_TYPE_DERIVED_FROM` is its own distinct open-world relationship type (`KNOWN_RELATIONSHIP_TYPES`), never written to `workspace.supersessions` and never confused with `share_case`/general Copy — those remain entirely separate mechanisms.

**Visibility, resolved per Constitutional Invariant 11:** the derived Case always begins `CASE_VISIBILITY_PRIVATE`, regardless of the archived source's own visibility (Private, Shared, or Collaborative alike) — creating a new working object is never itself an act of sharing. The archived source's own `visibility` field is never touched by derivation. Route wiring: `derive_case` (`POST /projects/<project_id>/workspace/cases/<case_id>/derive`, `case_id` here is the archived source; redirects into the newly created derived Case on success). `case_workspace.html`'s case list shows a "Derive Active Case" button in place of the (now-hidden) Share/Retract/Archive controls once a Case is archived, for its owner or an admin-role actor. Tests: `tests/test_case_derivation.py` (29 tests).

### Selective Adopt / Carry-Forward — implemented, deliberately narrow object scope (Finding + ReviewMessage only)
`case_workspace.py`: `CaseWorkspaceStore.adopt_finding_into_case` and `adopt_review_message_into_case` are the only two supported carry-forward operations — "history remains where it happened; what still matters may be deliberately carried forward." Both require the source item's own Case to be `CASE_STATUS_ARCHIVED`, the target Case's `derived_from_case_id` to equal that source Case's id (carry-forward is only defined from an archived Case into its own recorded derivation, never an arbitrary destination), and owner-or-admin authority checked **against the target Case** (`_validate_carry_forward_authority`, the shared validation helper both methods call) — "unauthorized participants must not carry historical material into another person's private derived Case" is a statement about who controls the destination. Nothing is carried forward automatically by Derive itself; adoption is always a separate, explicit, per-item human act. No adoption path exists for `Disposition`, `ReviewerValidation`, `RequirementAdjudication`, `AnalysisRun`, or `Attention` — the object scope is closed by omission (only two `adopt_*` methods exist on the store at all, asserted directly in `tests/test_case_adoption.py::test_unsupported_object_types_have_no_adoption_path`), not by a runtime type-check that could silently expand later. See `specified-unbuilt/investigation-lifecycle-extensions.md` for why each excluded type was excluded.

**New governed primitive, `CarriedForwardAdoption`** (`workspace.carried_forward_adoptions`, one list per project) — the single, uniform, directly-filterable record answering "which active items in a Case were carried forward, from which historical item, by whom, when, from which predecessor Case," queried via `CaseWorkspaceStore.carried_forward_adoptions_for_case`. Deliberately not a reuse of the `Relationship` substrate (unlike Derive's own `RELATIONSHIP_TYPE_DERIVED_FROM`): `Relationship` has no source-Case/target-Case concept, and reconstructing that from a bare from/to-object edge would need an extra `_cases_referencing_object`-style join on every query — this record captures `source_case_id`/`target_case_id`/`object_type`/`source_object_id`/`successor_object_id`/`adopted_by`/`adopted_at` directly. `object_type` is open-world (`KNOWN_CARRIED_FORWARD_OBJECT_TYPES` — `"finding"`/`"review_message"` today), matching `Supersession`'s own precedent for extensible-but-currently-narrow typed lineage.

**Finding carry-forward — the original Finding is never touched, moved, or re-cased.** A genuinely new `Finding` is created in the target Case (new id, `claim_status=FINDING_STATUS_PROVISIONAL` — Finding's own ordinary default, never anything stronger) because continued review (`ReviewerValidation`/`Disposition`/Apply) requires a real, mutable Finding, not a read-only reference — an old conclusion never silently becomes current truth merely by being carried forward; renewed `ReviewerValidation`/`Disposition` is required exactly as for any other Finding (Apply's existing Confirmed-Disposition gate is untouched and still enforced). Finding has no generic related-object pointer of its own, so per-item provenance back to the original rides on the accompanying `AnalysisRun`'s `AnalysisTrigger.trigger_reference_type`/`trigger_reference_id` (`engine_name="carry_forward_adoption"`) — existing fields reused rather than a new one added to `Finding`, mirroring `promote_requirement_item`'s own precedent of creating an honest accompanying `AnalysisRun` rather than fabricating provenance. `Finding`/`AnalysisRun`/`CarriedForwardAdoption` are written in exactly one `self.save(workspace)` call.

**ReviewMessage carry-forward — the original message and its thread are never touched.** A new `ReviewThread` (anchored to the target Case) + `ReviewMessage` are created so the reconsideration can actually be discussed/resolved in the target Case's own live context. `actor` on the new message is the **adopting** actor, never the original commenter — "the original commenter must not falsely become the author of the new active item," and the reason an unavailable/former contributor is never a blocker: nothing requires them to act again. The original voice is preserved without misattribution: `text` quotes the original verbatim inside an explicit "[Carried forward from archived Case ...]" frame (plus an optional adopting-actor `note`), and `ReviewMessage`'s own existing `related_object_type`/`related_object_id` fields (no new field needed) point directly at the original message — `message_type=MESSAGE_TYPE_CARRIED_FORWARD` (new, open-world, `KNOWN_MESSAGE_TYPES`). `ReviewThread`/`ReviewMessage`/`CarriedForwardAdoption` are written in exactly one `self.save(workspace)` call.

Privacy: adoption never changes either Case's `visibility` — the target Case (already `PRIVATE` per Derive) stays exactly as it was, and the archived source's own visibility is read-only throughout. Route wiring: `adopt_finding` (`POST /projects/<project_id>/workspace/cases/<case_id>/adopt-finding`, form field `finding_id`) and `adopt_review_message` (`POST /projects/<project_id>/workspace/cases/<case_id>/adopt-message`, form fields `message_id`/`note`) — `case_id` in both is the TARGET (derived) Case. **No picker UI was added this tranche** — these routes exist for programmatic/future-UI use, matching the tranche's own scope discipline around avoiding a broader UI build; selecting *which* historical item to adopt currently requires knowing its id directly. Tests: `tests/test_case_adoption.py` (31 tests).

### `promote_requirement_item()` — implemented (ratified governance baseline tranche)
`case_workspace.py`, method on `CaseWorkspaceStore`, immediately after `requirement_adjudication_state`. Bridges a `RequirementItem` (`services/bhive_parser.py`'s legacy extraction pipeline, still-decoupled by design — this module does not import `bhive_parser`) into a governed `Requirement`. `source_id` has no default and cannot be omitted (`TypeError` if the caller tries) — no inference path exists. Creates the Requirement's accompanying `Finding` + `AnalysisRun`/`AnalysisTrigger` (preserving extraction confidence and an explicit, caller-supplied trigger) and the `Requirement` itself (`registration_method=REQUIREMENT_REGISTRATION_MACHINE_EXTRACTED`) in memory, then writes all three in exactly one `self.save(workspace)` call — the same single-save-per-governed-operation pattern `register_table_evidence` already uses, so a failure between records is structurally impossible, not just tested for. Never sets `Requirement.status` to anything but its ordinary default and never creates a `Disposition`/`RequirementAdjudication` — the promoted Requirement is exactly as un-adjudicated as a manually-registered one. Route wiring: `routes/workspace.py`'s `promote_requirement_item_route` (`POST /projects/<project_id>/workspace/cases/<case_id>/requirement-items/<requirement_item_id>/promote`), form-required `source_id`, `AnalysisTrigger(trigger_type=ANALYSIS_TRIGGER_USER_INITIATED, triggered_by_actor=<reviewer>)` constructed from the real requesting session. Tests: `tests/test_requirement_promotion.py` (19 tests: 14 store-layer, 5 route-layer).

### Project Operating Environment — implemented (CLAUDE-P29, locked-classification tranche)
`services/environment_capabilities.py` (new module — a closed enum plus a strict validator plus one concrete capability mapping, deliberately not a plugin/registry framework): `CLIENT_OWNER`/`DESIGN_BUILDER_PROPONENT`, `OPERATING_ENVIRONMENTS` (the closed tuple — no `"other"` escape hatch exists, unlike `KNOWN_PARTICIPANT_ROLES`), `is_valid_operating_environment`, `allowed_participant_roles`. Answers a question no existing mechanism answered: which side of a procurement/delivery relationship (Client/Owner vs. Design-Builder/Proponent) is this *project's workspace itself* configured to serve — fixed once, at project creation, for the life of the project. This is deliberately **not** the same concept as `represented_party_by`/`PerspectiveAssessment` (the existing per-reviewer comparative mechanism, CLAUDE-P12R/P17, unmodified by this tranche) and **not** the governed, still-`NOT AUTHORIZED` "Perspective" object in `specified-unbuilt/perspective-and-contract-dna.md`: `represented_party_by` is mutable, per-reviewer, and answers "whose eyes am I reading this Finding through today, within one shared project"; Operating Environment is immutable, project-wide, and answers "which side is this entire workspace instance structurally configured for" — a coarser, one-time, higher-stakes classification that gates which `Participant.role_type` values are even selectable (`allowed_participant_roles`), not which lens a reviewer applies to shared content. A reviewer changing their `represented_party_by`, or a Case's Private/Shared/Collaborative visibility changing, has no code path that can reach `operating_environment` — the two mechanisms share no mutation logic.

`ProjectWorkspace.operating_environment`/`operating_environment_set_by`/`operating_environment_set_at` (new fields, default `None` — a pre-P29 project loads with `operating_environment=None`, never a fabricated value). `CaseWorkspaceStore.set_operating_environment` is the single, centralized write gate: validates against `is_valid_operating_environment` (rejects, does not silently coerce, an unrecognized value — the deliberate opposite of this codebase's dominant `normalize_open_world_value` open-world-preserving pattern, which is the wrong shape for a field that must be a closed, structurally-gated enum), then raises the new `OperatingEnvironmentAlreadySetError` (a `CaseWorkspaceError` subclass) if the field is already non-`None` — no other method anywhere writes this field, so there is exactly one place immutability could fail, and it is tested directly (service-layer direct-call, forged-route, and same-value-resubmission cases all covered). Logs an `operating_environment_established` `GovernanceLog` event (`previous_state`/`operating_environment`) in the same call, atomic with the field write.

**Creation path:** `services/ingestion.py`'s `ingest_upload` now takes a required `operating_environment` argument (no default — the same "no inference path exists" discipline as `promote_requirement_item`'s `source_id`), validated before any file/parsing work begins, and the `ProjectWorkspace` is now created eagerly (previously lazy, only when `project_name` was given) so `set_operating_environment` always has a workspace to lock immediately after creation — every new project is classified atomically at birth, never in a separate step where an unclassified project could transiently exist. Route wiring: `routes/portal.py`'s `/upload` (two-entrance gateway in `templates/gateway.html`, pre-selecting the environment via `?environment=`) and `routes/api.py`'s `ingest_document` both require and pass this field through; a missing/invalid value is rejected with 400 before ingestion starts, leaving no project behind.

**Historical/legacy projects:** a pre-P29 workspace simply has `operating_environment=None` — never backfilled or inferred. `routes/workspace.py`'s `classify_operating_environment` (`POST /projects/<project_id>/workspace/classify-environment`, `@admin_required` — the same authority level as project creation itself, since this codebase has no separate "project owner" concept for `ProjectWorkspace` to check against) is the one-time path to establish it for such a project, calling the identical `set_operating_environment` gate — not a separate, weaker mechanism, and refuses exactly the same way on a second attempt. `case_workspace.html` offers the classification form only while `operating_environment` is still `None`, and never offers any control once it is set.

**Environment-dependent behavior, kept narrow and honest rather than speculative:** the one implemented differentiation is `allowed_participant_roles(operating_environment)` gating which `Participant.role_type` values `register_participant_route` (`routes/workspace.py`) accepts — Client/Owner projects admit `owner`/`consultant`/`other`; Design-Builder/Proponent projects admit `design_builder`/`contractor`/`proponent`/`other`; a legacy `None` environment returns `None` from this function, meaning "no gating, full `KNOWN_PARTICIPANT_ROLES` allowed" — deliberately preserving every pre-P29 project's existing behavior unchanged. No new AI-prompt content was written for this tranche — extending `services/bhive_parser.py`'s adversarially-tuned prompts to be environment-aware was deliberately out of scope, consistent with this codebase's standing caution around that module.

**Export stamping:** `services/rfi_export.py`'s `build_rfi_docx`/`build_rfi_draft_docx` both gained an optional, additive `operating_environment_label` parameter, stamped into the exported `.docx` metadata block when supplied. `routes/api.py`'s own unauthenticated-turned-authenticated RFI export was left unstamped as of this tranche — it only has `RequirementsRegistry` access, not `CaseWorkspaceStore` — **closed in CLAUDE-P30, see that entry below.**

Tests: `tests/test_operating_environment.py` (29 tests — creation requirement, persistence/reopening, immutability at service/route layers, role/perspective independence, capability gating, cross-environment project isolation with a shared source document, historical/legacy one-time classification, export stamping) plus `tests/test_forward_ingestion_metadata.py` (updated for the new required `ingest_upload` parameter).

### Environment Capability Architecture — implemented (CLAUDE-P30, capability-grammar + RFI directionality + Go/No-Go tranche)

### Project-Level Access Control — implemented, bounded (CLAUDE-P32)

**The gap this closes, confirmed by direct investigation, not assumed:** `governance/specified-unbuilt/tenancy-and-project-authorization.md`'s own CLAUDE-P27 finding — any authenticated user, `admin` or `read_only`, could open any project by knowing or guessing its `project_id` — remained true through CLAUDE-P29/P30/P31, each of which built locked-environment/capability/security-governance machinery on top of an object model any logged-in account could still fully read. ### `Folder` — implemented, bounded (CLAUDE-P40-VW9, Governed Files Display and Project File Architecture)
`services/case_workspace.py`: `FOLDER_ROOT_DATA_ROOM`/`FOLDER_ROOT_DESIGN_BUILDER`/`KNOWN_FOLDER_ROOTS` — a closed, two-value vocabulary (unlike `Source.kind`'s open-world shape) naming two DIFFERENT GOVERNANCE SPACES: Data Room (controlled, externally-issued material) and Design-Builder Workspace (editable, team-organized material). Both roots are GOVERNED VIRTUAL roots — neither is itself a persisted `Folder` record; a project's `workspace.folders` holds only real, user-created Design-Builder Workspace folders. `create_folder` has no `root` parameter at all and unconditionally writes `FOLDER_ROOT_DESIGN_BUILDER` — there is structurally no route or method in this codebase that can create a Data Room folder record this stage, making "ordinary Design-Builder actions cannot reach Data Room" true by construction, not merely by convention.

`Folder` dataclass (`id`/`project_id`/`root`/`name`/`created_at`/`created_by`/`parent_folder_id`/`removed_at`/`removed_by`). Canonical identity is `id` (uuid4 via the same `_new_id()` every other record uses) — mirrors the exact principle `Source`'s own docstring already states ("folder locations and filenames are external representations only"). A folder's full path is always DERIVED at read time by walking `parent_folder_id` (`CaseWorkspaceStore._folder_path`, root-most first) — never stored as a string, the same "store flat, derive structure at read time" shape `visible_cases_for` and everything else in this module already use. `ProjectWorkspace.folders` (new `list[dict]` field, empty-list default) is purely additive — a legacy workspace predating this stage simply lacks the key and loads with the default, identical to `tags`/`tag_occurrences`/`tasks`' own precedent; directly verified by stripping the key from a real persisted workspace JSON and confirming it still loads and can create folders going forward.

**Mutation methods, no owner/admin gate.** `create_folder`/`rename_folder`/`move_folder`/`delete_folder` are reachable by any project-authorized actor — deliberately mirrors `create_task`/`create_custom_tag`'s own precedent (no authority check beyond project access) rather than `remove_source`/`remove_project`'s owner-or-admin pattern, since Design-Builder Workspace is explicitly "editable working organization created by the Project team" — collaborative team structure, not owner-controlled evidence. `create_folder`/`rename_folder` enforce sibling-name uniqueness scoped to (project, root, parent) via `_reject_if_sibling_folder_name_taken` (style mirrors `services/ingestion.py`'s own `_reject_if_name_taken` — exact-match string comparison, short plain error, no id leaked, though narrower in scope: sibling-only, not whole-registry). `move_folder` prevents cycles via `_folder_descendant_ids` (rejects moving a folder into itself or any of its own descendants) and refuses a foreign-project/removed/non-Design-Builder destination. `delete_folder` refuses a non-empty folder outright and is a recoverable soft-delete (`removed_at`/`removed_by`) — the same tombstone convention `Source`/`Project` already establish (Constitutional Invariant 5: correction is non-destructive) — though deliberately no restore UI was built this stage (the data stays recoverable; a future stage could add a "Removed Folders" surface analogous to Removed Items/Removed Projects).

**Project-boundary enforcement, verified in two independent ways, not just one.** A folder id from a different Project is unreachable through the ordinary route path (each Project's `CaseWorkspaceStore` state lives in its own file, so `workspace.folders` can only ever contain that Project's own records) — but `rename_folder`/`move_folder`/`delete_folder` ALSO independently check the found record's own `project_id` field against the calling workspace before acting, mirroring `Source.project_id`'s own defensive shape. Both guards were directly falsified during this stage's own review (each temporarily disabled, confirmed the relevant test genuinely failed, then restored) — the structural guard alone does not protect against a corrupted/hand-edited record whose own `project_id` disagrees with the file it's found in, which is exactly the scenario the second, explicit check exists for.

**No `folder_id` field exists on `Source`.** A Document cannot be assigned into a Folder in this slice — Document identity and every existing Investigation/RFI/Task/Tag/conversation/citation relationship (all keyed off `Source.id`, never location) are completely untouched by this addition, both now and by construction for whatever a future stage adds. Route wiring: `routes/workspace.py`'s `create_folder_route`/`rename_folder_route`/`move_folder_route`/`delete_folder_route` (`/projects/<id>/workspace/folders...`), authorized exactly like every other route via `_load_workspace_or_404` — no new authorization path. `show_workspace` gained a Files-specific resolution block (`open_folder`/`folder_ancestors`/`design_builder_children`/`design_builder_move_targets`/`data_room_sources`), computed only when the new `STABLE_DIRECTORY_KINDS["files"]` stable-directory-kind (the second real entry in the CLAUDE-P40-VW8-QA1 extension point) is the active view.

**File lifecycle vocabulary — named, documented, deliberately not implemented.** `linked → retrieved → ingested → used → preserved`, evaluated against this stage's own governing prompt: `ingested` is the only state genuinely real today (a Document is a first-class `Source` record — true since long before this stage, unchanged by it); `linked`/`retrieved` describe pre-`Source` states with no record type yet; `used` is inferable only by querying existing Finding/Requirement/Relationship references (no stored field — the natural future shape is a DERIVED property, matching `review_state_for_finding`'s own "derive at read time" precedent, not a new stored flag); `preserved` is partially precedented by `Source.file_hash` (exists, optional, unenforced) and `Supersession` (already real) but not wired to any actual immutability gate. No code path marks an existing Document with any of these four unimplemented states merely to populate the Files interface.

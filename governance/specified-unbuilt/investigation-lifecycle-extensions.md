# Specified But Unbuilt — Investigation Lifecycle Extensions and Deficiency

**Status:** Specified, not implemented. Extends the implemented `Case`/`CaseRecord` (see `current/kernel-object-model.md`).

## Lifecycle

Private → explicit Share/Publish → Shared → (first governed, non-owner-attributed contribution) → Collaborative → Archive.

**Capability-level status, precise, not blanket:** **Private → explicit Share → Shared → (first governed non-owner contribution) → Collaborative, pre-Collaborative Shared → Private retraction, terminal Archive from any of Private/Shared/Collaborative, and Derive (Archive → new active Case) are all now implemented** (Case-visibility, collaboration-threshold, Archive, and Case-lineage tranches; see `current/kernel-object-model.md`'s "Case visibility", "Collaboration threshold + pre-collaboration retraction", "Case Archive", and "Case Archive → Derived Active Case" entries for the code/test anchors). **`CaseLock`, general Copy/Adopt (selective carry-forward beyond Derive's own fixed minimal-context rule), automatic predecessor-issue applicability analysis, and publication anchoring remain specified but unbuilt**, exactly as below — this document's overall "Specified, not implemented" status line (top of file) applies to those, not to the whole document, and the reverse holds too: implementing Private↔Shared↔Collaborative↔Archive↔Derive does not mean CaseLock/Copy/Adopt/applicability-analysis/publication-anchoring are implemented. **Archive's own implementation confirmed and made explicit the two-axis correction this document's "Archive is terminal" section already anticipated by describing Archive as a lifecycle state distinct from sharing:** `status` (OPEN/ARCHIVED) and `visibility` (PRIVATE/SHARED/COLLABORATIVE) are separate fields/axes on `CaseRecord`, not one enum — ARCHIVED was never added as a fourth `visibility` value.

**Collaboration threshold, precisely enumerated and now implemented exactly as specified here, with two boundary decisions resolved (not left as silent defaults):** fires on the first governed write by an actor other than the owner, from any of: `ReviewMessage.actor` (human `origin` only), `Relationship` confirmation via `confirmed_by` (referencing this Case's Findings/Sources — resolved to use confirmation rather than creation, since a Relationship's `created_by` has no structural guarantee of being human; see `current/kernel-object-model.md`), `ReviewerValidation.reviewer`, `Disposition.reviewer`, `AnalysisTrigger.triggered_by_actor` restricted to `ANALYSIS_TRIGGER_USER_INITIATED` (for analyses attached to this case), non-owner `Attention` creation on a thread anchored to this Case. Explicitly excluded: mere viewing (never tracked at all, by anti-surveillance design); `Snapshot` creation by a non-owner (project-wide, not investigation-specific). **`Activity.created_by`, listed here originally as a candidate qualifying write, is now excluded** — implementation found it has no origin field distinguishing machine from human authorship and zero real callers to establish a convention, so counting it risked exactly the false machine-boundary crossing the ratified spec prohibits; revisit if Activity later gains its own origin field. **The previously-flagged boundary case is now resolved, not left open:** a non-owner adjudicating a Requirement whose evidence references this Case's Findings does **not** count — implemented that way, reasoned in `record_requirement_adjudication`'s own docstring.

Pre-threshold: owner may retract Shared→Private (implemented: `retract_case_to_private`). Post-threshold: prohibited (implemented: rejected at the same method's validation gate) — this preserves shared provenance, not authorship (constitutional invariant 12).

**Archive is terminal (constitutional invariant 13) — implemented.** Readable/searchable per existing visibility rules; never receives new comments, findings, relationships, evidence, or adjudications — enforced centrally via `CaseWorkspaceStore._require_case_not_archived`, see `current/kernel-object-model.md`'s "Case Archive" entry. "Reopen an archived Case" does not survive as a concept — removed from the model entirely, and no method implements it.

**Derive — implemented, narrower than originally sketched here, deliberately.** New reasoning proceeds through **Derive** (implemented field name is `CaseRecord.derived_from_case_id`, not the `derived_from_investigation_id` name originally sketched in this paragraph — same concept, named after the object it actually points at; chosen over "Copy"/"Adopt" specifically because it's ownership-neutral, correct whether the same owner extends their own scope or a different reviewer takes over frozen work): new permanent identity, explicit structural lineage (both a denormalized `CaseRecord` pointer and an authoritative `Relationship` of type `derived_from`, queryable in both directions — see `current/kernel-object-model.md`), source unchanged forever. **What's implemented is specifically "copy minimal working context (title/objective/source references), reference the rest" — not general Copy/Adopt.** Selective carry-forward of specific historical items (choosing which comments/Findings to bring along), and automatic predecessor-issue applicability analysis (surfacing which of the archive's open issues might still apply to the derived Case), are both explicitly named future capabilities, not implemented and not implied by Derive's current fixed, minimal, all-or-nothing working-context rule. **Comparable/exportable remain unbuilt.**

**`CaseLock`, relocated off Archive entirely.** A temporary, reversible write-suspension on an *active* Case only (e.g., during managerial review) — always PM/authorized-role-gated. Archived material cannot be locked; there's nothing left to suspend that isn't already permanently frozen. "Unlock" is the only surviving relative of "reopen," and it never applies to archived material.

**Authority as actually implemented — a deliberate, documented simplification of this section's original design, not a silent deviation:** this codebase has no PM/manager role distinct from `admin`/`read_only` (see `models.py`), and the Archive tranche's own authorization explicitly required using "the narrowest existing legitimate pattern" rather than inventing new role architecture. The implemented rule is therefore owner-or-admin, **uniformly regardless of collaboration state** — not "owner alone pre-threshold, PM-gated post-threshold" as originally sketched here. Archiving collaborated-on work does not require a different authority tier than archiving private work; the admin-override path exists so an unavailable/former owner never permanently blocks archival, not to gate collaborative Cases specifically. If a real PM/manager role is later introduced, this paragraph's original post-threshold PM-gating intent should be revisited — it was not rejected on the merits, only deferred against a role that doesn't yet exist; `CaseLock` remains a candidate for that same real PM-gating once such a role exists. **Derive's actual implemented authority is stricter than "ordinary read/visibility access" originally sketched here**: it requires the same owner-or-admin pattern as `archive_case` (the archived source's own creator, or an admin-role actor) — not mere read access to the archive. This was a deliberate tightening, not an oversight: an archived Case may be readable by more people (per its pre-archive visibility) than are authorized to spawn new active work from it. General Copy authority, if built later as its own separate capability, remains an open question for that future tranche.

## Publication anchoring

Two separate mechanisms at two separate grains, deliberately not one overloaded mechanism: **(A)** a cheap, Case-scoped content-plus-`project_state_version` anchor, captured at every Share/Publish act — proportional to the investigation's own size. **(B)** the full project `Snapshot`, decoupled from per-share frequency — optional, prompted, or maintained on an independent cadence, never triggered automatically by every individual share (a full-project Snapshot on every share would be proportional to total project size, not the shared item, and was tested and rejected for exactly that reason).

## Deficiency / completion-resolution

A distinct, thin kernel primitive (not a Finding-status extension, not a Disposition/RequirementAdjudication variant) — tested precisely: those three answer "what was observed," "what happens to this Finding," and "does evidence satisfy this Requirement" respectively; Deficiency additionally answers "who must correct it, by when, how was it corrected, who verified it, is it closed" — a multi-step, two-actor-role, due-date-bearing lifecycle none of the three existing objects are shaped for.

Composes from existing primitives rather than duplicating them: `Relationship` (link to originating Finding/Requirement/spec), `TemporalObligation` (correction due-dates), and an **append-only event sequence with a derived current status** — the same discipline behind `review_state_for_finding`/`requirement_adjudication_state` — rather than a mutable open/closed field. Minimum lifecycle: Identified → (Correction Required) → Correction Submitted → Verification Attempted → Verified/Accepted **or** Verification Failed (loops back, prior attempts preserved, never erased) → Closed (explicit, authorized act).

**Substantial Completion, Occupancy/Turnover, and Final Completion are distinct milestone events**, not derived from deficiency-count math and not hard-coded legal definitions — each grounded in an actual certificate/notice `Source` document, with Contract DNA offering only an expected template (never the actual date or criteria). A project may reach Substantial Completion, and later Occupancy, with an open Deficiency list; this is not a gap, it's the documented reality this design deliberately accommodates.

Unresolved deficiencies transition (non-destructively — marked transitioned, not falsely closed) into seasonal/warranty `TemporalObligation`s, or, where the delivery model requires it, link toward an eventual Maintenance Obligation — a **connection point only**, via `Relationship`'s already-open-world nature, not a design of the Machine Model layer (see `deferred-reserved/reservations.md`).

BEEHIVE should eventually answer deficiency-completion questions (how many remain, which are material, which block milestones, which are overdue) with **factors kept individually visible, never collapsed into a single project-health score** — the same discipline already required for `ViabilityAssessment`.

## `promote_requirement_item()` — implemented; this section now records the ratified design history

Bridges `RequirementItem` (legacy extraction pipeline) into the governed `Requirement` primitive, using the already-existing, previously-unused `REQUIREMENT_REGISTRATION_MACHINE_EXTRACTED` registration method. The contract, finalized this engagement: promotion must not discard confidence, reasoning, triggering condition, or provenance. Concretely, promotion **creates an accompanying `Finding`** carrying the extraction confidence and an explicit `AnalysisTrigger` (`ANALYSIS_TRIGGER_USER_INITIATED`/`AGENT_INITIATED`), and the promoting actor must **actively assert** a real `source_id` — never inherit one implicitly — satisfying the no-silent-provenance-fabrication discipline established this session.

**Implemented, tested, and route-wired** — see `current/kernel-object-model.md` for the code anchor, exact behavior, and test count. This section is preserved as the design record the implementation was built against, per `governance-of-governance/amendment-and-ratification.md`'s own preserved-not-edited-away discipline for how a specified item moves to current status.

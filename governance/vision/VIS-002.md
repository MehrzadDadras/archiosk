## Vision statement

> Before creating a new primitive, look for a useful composition of existing
> primitives — and where a genuinely missing primitive is found, build it small and
> stable enough that it multiplies what the other primitives can do.

That statement is `GO-TOOL-MAKING-01`'s own preserved prompt text, quoted rather
than paraphrased.

## Product intent

Capability should grow by recombination rather than accumulation. The intent is a
system where a new need is first tested against what already exists, and where the
things that do get built are chosen for how much they multiply the rest — not for
how much surface area they add.

The `developer-mode-ccn.md` framing names the failure this avoids: **console
sprawl**. A product that answers every new need with a new permanent control ends up
with a control panel instead of an interface.

## Why it matters

It is the difference between a product that gets richer and one that just gets
bigger. It also sets an expectation for how agents should approach capability
requests: search for a composition first, propose a primitive second, and treat a
new primitive as something that must justify itself by what it enables elsewhere.

## What it enables

**Implemented today (evidenced):**

- An **application capability registry** exists — `GO-TOOL-MAKING-01` records it as
  "confirmed implemented", built under separate governed work.
- Composable inspection through the Composer rather than per-capability controls —
  the kiosk shape described in [`VIS-001`](VIS-001.md), which is implemented.

**Not implemented (evidenced as unbuilt):**

- **Tool generation of any kind.** `GO-TOOL-MAKING-01`'s own status is explicit:
  *"generation workflow remains unbuilt."*
- GO recognising that capabilities can be composed into a new internal tool.
- GO proposing or generating a bounded tool package.
- Any lifecycle for a generated tool — authoring, review, registration, versioning,
  retirement.

**This record deliberately does not describe the unbuilt half as though it partly
exists.** The capability registry is not a tool-generation system, and calling it a
step toward one would overstate the evidence.

## What it does not authorize

- **It does not authorize building the generation workflow.** That remains
  `GO-TOOL-MAKING-01`'s unbuilt scope and needs its own Product Owner authorization
  and implementation order.
- **It does not authorize GO proposing or creating tools** in any surface, including
  Developer Mode.
- **It does not authorize new primitives** on the argument that they would multiply
  others. The vision says *prefer composition*; it grants no licence to add.
- **It does not authorize removing existing controls** to reduce console sprawl.
  Surface changes remain governed by [`GOV-P-002`](../records/GOV-P-002.md),
  `CIC-PANEL` and `CIC-PAGE-TEMPLATE`.
- **It does not relax any authority boundary.** The source record is explicit that
  this direction preserves "provenance, reversibility, authority, and explicit
  approval boundaries" — a generated tool would be subject to all of them.

## Distinct programme identity

Repository evidence confirms Navigation Context is distinct. `CLAUDE-GO-NAVIGATION-CONTEXT-GAMES-01` produced a governed operational map of settled facts, open defects, dispositions, and reference patterns; a bounded Composer-hotlink origin-pointer pilot is implemented and registered in the UI reference map.

It is not wholly owned by:

- **Living Knowledge**, which concerns connected, evolving project understanding and contextual knowledge traversal;
- **Composer**, which can originate or explain a navigation path but does not own the workspace's navigation contract;
- **Voice/Ushering**, which may suggest where to go but does not establish return-state mechanics;
- **River**, whose relationships may provide paths but do not determine navigation purpose, current context, or return behaviour.

## Evidence-supported principles

- Navigation understands and validates the current project and object context.
- Entering deeper evidence should preserve an honest return path where the originating purpose matters.
- The system should help users understand where they are, what they are looking at, and why they arrived there.
- Project, Source/document, Requirement, Finding, Case, evidence, and relationship records may provide navigable paths when their canonical identity and access rules are preserved.
- Context may survive refreshes, view transitions, and project round-trips only where the implemented state model supports that persistence truthfully.
- A stale, missing, foreign-project, or unauthorized target must degrade safely rather than leak or fabricate context.
- Navigation state, selection, and display position are not project truth.
- An origin pointer must never become an authorization boundary of its own.

## Current implemented foundations

The repository already establishes several bounded foundations:

- every route resolves canonical objects by project-scoped machine identity rather than mutable display name;
- `Anchor` is an existing open-world “what this is about” pointer;
- Requirement and Finding selection persist in a project-scoped session slot across ordinary refresh and navigation, while remaining explicitly non-authoritative and clearing on sign-out;
- a Composer Source hotlink may carry `origin_message_id` and return to the originating message;
- the accepted pilot demonstrated that a sufficient return envelope can require more than one object ID—the conversation's Case context was also necessary;
- existing RFI preview redirects demonstrate purpose surviving a redirect;
- canonical shelf membership is re-derived from project state and is not corrupted by where an object was opened from.

These foundations do not constitute a universal trajectory or return-path system.

## Return-path discipline

The canonical operational map identifies missing origin or purpose state on most internal links as a major general navigation defect. Its accepted pilot establishes a bounded reference pattern, not permission to add return parameters indiscriminately.

Future work must discover the minimum sufficient return envelope experimentally. It must preserve project isolation, canonical identity, privacy, authorization, and honest degradation. A generic browser-back heuristic is not automatically equivalent to a governed return to the originating project purpose.

## Relationship to Living Knowledge

[GO-LIVING-KNOWLEDGE-01](GO-LIVING-KNOWLEDGE-01.md) may use navigation paths to traverse evidence, decisions, history, and understanding. Navigation Context governs orientation, transition, and return mechanics; Living Knowledge governs the broader body of knowledge being traversed. Neither absorbs the other.

## Relationship to Composer and Voice

[GO-COMPOSER-01](GO-COMPOSER-01.md) can produce evidence hotlinks and contextual follow-ups. [GO-VOICE-01](GO-VOICE-01.md) can usher a user toward a relevant surface. Both must reuse the canonical navigation and capability conditions rather than create alternate routes, and neither may imply that a suggested destination confers authority.

## Relationship to River

[GO-RIVER-01](GO-RIVER-01.md) relationships can provide meaningful routes among project objects. A River path explains a governed relationship; a navigation path records or projects user movement and purpose. Do not collapse them or infer causal meaning from navigation history.

## Programme boundary

This record does not authorize a generalized origin-envelope schema, trajectory store, breadcrumb redesign, universal return control, new route state, navigation UI, or runtime changes. The existing operational map, implemented pilot, and current context-persistence rules remain authoritative.

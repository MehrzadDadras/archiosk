## Confirmed entry model

The preferred gateway is:

- **New Project**
- **Open Existing**

Users should not be forced through separate Client-side and Builder-side application gateways. Project identity and operating environment belong to the project, not to a superficial login branch.

The operating environment is established when the project is created and then governs behavior inside that project. It is a canonical project property, not a cosmetic UI toggle. Correction is an authorized administrative action requiring governed reason and provenance, not casual user switching.

Downstream permissions, workflows, information barriers, participant roles, and available actions derive from governed project context. A project previously placed under the wrong side should be corrected through project governance rather than used to justify maintaining two entry applications.

## Current implementation lineage

Repository evidence confirms that `CLAUDE-GO-NEUTRAL-ENTRY-01` retired the former duplicated Client/Owner and Design-Builder/Proponent gateway actions and replaced them with one neutral New Project action and one authorized-project opening surface. The already-implemented Project Operating Environment remained intact and governed.

Later entry evolution retired the separate authenticated Gateway template and projected the same entry functions into the unified post-sign-in surface. That physical relocation does not supersede Neutral Entry. Current routes, labels, authorization checks, and surface references in the UI Reference Map remain implementation truth.

## Information-barrier boundary

Neutral entry does not permit Client/Owner and Proponent/Builder evidence to mix. Information becomes available only according to governed lifecycle and formal publication state. Until then, barriers remain intact, including for blind Client → published RFP → Builder-side proving exercises.

Project and tenant isolation, owner/proponent role restrictions, RFI directionality, export and issue permissions, and confidential-evidence boundaries remain authoritative. A unified gateway is never an authorization bypass.

## Relationship to RFP publication

A Client-side project corpus may be developed and corrected privately and then formally published to proponents. Builder-side GO must not see unpublished Client-side working evidence. Neutral Entry unifies how a user enters ARCHIOSK; it does not merge project worlds, evidence populations, or authorities.

## Relationship to project creation

The project operating environment is established during project creation and persists as governed project state. Existing repository governance permits a bounded administrative correction path with a required reason; it does not permit ordinary users to switch environments casually.

Do not infer additional operating-environment values, publication transitions, or capability rules beyond those implemented or separately governed.

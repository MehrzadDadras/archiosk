## Exact prompt text

```text
CLAUDE-HOLODECK-WORLDS-SPIN-01
Reconstitute the Holodeck World Model and Advance Spin Through Worlds
Product Owner Direction

Do not treat this as a request to build a better report screen.

Do not treat this as a request to build another conventional dashboard.

Do not treat Spin as an isolated analysis service.

The governing product concept is the ARCHIOSK Holodeck as a project world system.

The immediate goal is to recover that architecture faithfully, connect it to the existing Spin / Helix / River / Composer / multimodal machinery, advance the Prompt-Spin-Games model inside it, and then run a real world/mode so the Product Owner can see the result.

1. Holodeck Is the Governing Container

The Holodeck is not merely a page.

It is the interactive project environment in which ARCHIOSK exposes project evidence, intelligence, relationships, tools, investigations, findings and project state.

Think less like:

dashboard → tabs → reports

and more like:

world → objects → environments → interactions → investigations → consequences

The project should feel enterable.

The Product Owner should be able to move through the project's evidence and intelligence rather than merely receive summaries from it.

The existing ARCHIOSK visual and interaction language must be inspected and reused rather than replaced casually.

2. Roblox Is an Architectural Metaphor, Not a Visual Style

The Product Owner previously used Roblox as a useful metaphor.

Do not imitate Roblox's appearance, branding, graphics or game mechanics.

The useful architectural idea is:

A common platform can host many different worlds made from shared underlying capabilities.

A world may have:

its own objective,
rules of attention,
available tools,
visible entities,
risks,
interaction patterns,
success/failure conditions,
and investigative strategies,

while still using the same underlying evidence and primitives.

ARCHIOSK should therefore avoid becoming one enormous hard-coded workflow.

Its intelligence should support different project worlds and modes composed from reusable machinery.3. World ≠ Primitive

Maintain a strict distinction.

Primitive

A reusable capability.

Examples may already exist for:

document reading,
multimodal inspection,
comparison,
revision detection,
relationships,
requirements,
evidence,
confidence,
authority,
scope,
structural units,
addressable regions,
traceability,
Composer,
River,
findings,
Spin execution.
Spin-Game

A bounded investigative move composed from one or more primitives.

Examples:

Change Game
Conflict Game
Missing Evidence Game
Assumption Game
Relationship Game
Propagation Game
Convergence Game
Revision Survival Game
Authority Game
Cross-Modal Game
World

A governed operating environment with an objective.

A world decides which kinds of evidence, relationships and games deserve attention.

Mode

A particular stance or operating condition inside a world.

For example:

Survival Mode

may radically increase attention to threats that could damage delivery, compliance, safety, cost, schedule, eligibility, contractual position or public trust.

Do not collapse these layers into one taxonomy.

4. Governing Primitive Rule

Before creating a new primitive:

Search for a useful composition of existing primitives.

When a genuinely missing primitive is discovered:

Build it as a small lubricated package with stable interfaces so that it multiplies what the other primitives can do.

This rule applies to Worlds and Spin-Games especially.

A new World should usually be a new composition and rule-set, not a new pile of duplicated capability.5. Preserve Helix / Progressive Project Convergence

The existing Helix concept remains foundational.

A project consists of independently evolving but interdependent strands such as:

requirements,
architecture,
structure,
mechanical,
electrical,
civil,
security,
operations,
commissioning,
procurement,
schedule,
cost,
authority,
approvals,
construction,
turnover.

These strands progress at different velocities.

Coordination quality is demonstrated by how well consequential strands progressively mesh at the maturity being claimed.

Spin is GO's governed mechanism for testing that mesh.

Do not reduce Helix to:

universal LOD numbers,
arbitrary maturity scores,
project-health percentages,
fixed discipline hierarchies,
or automated engineering judgement.
6. Prompt-Spin-Games Are the Investigative Machinery Inside Worlds

Advance the Prompt-Spin-Games concept.

A Spin-Game is not a fixed checklist and not merely a static prompt template.

It is a composable investigative strategy.

A game may:

detect something,
create a probe,
inspect related evidence,
follow relationships,
launch another game,
test convergence,
characterize uncertainty,
produce a finding or question.

Conceptual pattern:

Trigger → Game → Probe → Evidence → Relationship → Follow-on Game

Example:

A changed requirement is detected.

That may launch:

Change Game

which finds that the change affects an operational condition.

That may launch:

Propagation Game

which follows architectural, controls, commissioning and operational consequences.

That may launch:

Convergence Game

which tests whether those strands now mesh.

That may launch:

Missing Evidence Game

if expected downstream evidence is absent.

That may end in:

Evidence → Concern → Question

where human adjudication is required.

This is the intelligence that should operate inside a Holodeck World.7. Worlds Should Change the Rules of Attention

The same project evidence should be capable of producing different investigations depending on the World or Mode.

Do not simply run every game against every file.

A World establishes the purpose.

That purpose changes which signals become consequential.

For example:

Survival World / Survival Mode

Primary question:

What could hurt this project, pursuit or delivery if we fail to notice it now?

Possible areas of attention:

disqualification risk,
mandatory requirements,
conflicting instructions,
unresolved addenda,
hidden scope,
authority ambiguity,
design gaps,
unpropagated changes,
procurement traps,
schedule dependencies,
cost exposure,
safety consequences,
commissioning gaps,
operational incompatibility,
reputational/public-risk consequences,
evidence the team appears to be relying upon incorrectly.

The purpose is not paranoia and not indiscriminate flagging.

It is consequential survival-oriented investigation.

A strong Survival Spin should prioritize threats by evidence and consequence rather than count issues.

8. Other World Families May Exist — Do Not Hard-Code the Universe Yet

The architecture should permit additional Worlds to emerge from composition.

Potential examples include:

Coordination World

Where are consequential strands failing to converge?

Change World

What changed, and did the change propagate everywhere it needed to?

Comparison World

What differs between two evidence sets, revisions, schemes or states?

Requirement World

What is required, demonstrated, missing, ambiguous, superseded or contradicted?

Authority World

What governs, what has been displaced, and what remains uncertain?

Readiness / Commissioning World

Does downstream verification align with requirements and design intent?

These are examples, not a command to create all of them now.

Do not create a static catalogue simply because the names sound useful.

The first task is to prove the World architecture with one strong World.

9. First World to Prove: Survival Mode

For this prompt, use Survival Mode as the first proving World unless repository inspection reveals that an already-established World/mode is further advanced and would make a better non-destructive proof.

Survival Mode should be recognizable in three ways:

Objective

Find consequential conditions that could materially harm project success if overlooked.

Attention

Allocate investigative effort preferentially toward evidence and relationships associated with material consequence.

Game Composition

Dynamically select and chain suitable Spin-Games.

For example:

Change → Propagation → Conflict → Authority → Convergence → Missing Evidence

but only when the evidence warrants those transitions.

Do not hard-code this sequence.10. Gemini Document Review Should Enrich the Games

Recent Gemini document-review work identified useful concepts including the C6 granularity vocabulary and the C8 review-question family.

Do not create a parallel Gemini subsystem.

Recover and preserve the actual vocabulary available in current context or artefacts.

Use it to strengthen:

game scoping,
comparison,
change detection,
internal conflict detection,
assumptions,
missing information,
selective review,
reporting.

Important review questions include the class:

What is missing?
What changed?
What conflicts?
What assumptions appear to be made?
What differs?
What is inconsistent?
What needs further investigation?

The key is to make these questions playable through Spin-Games, not to merely add them as another checklist.

Where Gemini provides better exact vocabulary, preserve it.

11. Granularity Must Be Deliberate

A World or Spin-Game should be able to narrow or widen its scope deliberately.

Potential scopes may include:

entire project,
corpus,
document set,
document,
revision pair,
discipline,
requirement,
sheet,
page,
structural unit,
addressable region,
finding,
relationship chain.

Do not impose this as a rigid new ontology if existing GO or Gemini vocabulary is already established.

The important behaviour is:

Spin should know what level it is investigating and should be able to change that level intentionally.

12. Holodeck Should Reveal the World, Not Just Its Final Report

This is critical.

Do not finish by merely generating a text report.

The Product Owner wants to see the smarter Spin operating through the Holodeck.

Use existing application surfaces first.

The Holodeck should reveal, as far as current architecture permits:

current World / Mode,
Spin scope,
evidence being considered,
consequential entities/findings,
meaningful relationship chains,
games invoked,
discoveries that triggered follow-on games,
resulting findings,
uncertainty,
evidence trace,
and the final Spin summary/report.

Do not expose hidden chain-of-thought.

A concise inspectable trace is sufficient:

Why this game ran → what evidence triggered it → what it found → what it caused Spin to inspect next.13. The Holodeck World Should Be Navigable

Where the existing architecture allows it, findings should not be dead report rows.

A consequential finding should behave more like an enterable project object.

The Product Owner should be able to move from:

finding → source evidence → related evidence → relationship → consequence

and back.

This does not require inventing a 3D environment.

“World” refers to the interaction and composition model, not literal game graphics.

Preserve ARCHIOSK's existing restrained professional instrument character.

14. Repository-Grounded Audit First

Before modifying anything, inspect the existing repository and identify the machinery already available.

Pay particular attention to:

project workspace,

current online product surface.

Determine what can already be composed.

Do not trust programme descriptions over repository truth.15. Protect the Holodeck's Existing Product Intent

Do not casually redesign the Holodeck.

Do not replace it with a conventional SaaS dashboard.

Do not build a separate “Spin app.”

Do not create a parallel report portal.

Do not make the World metaphor into decorative labels pasted on existing tabs.

The World model should emerge from actual:

context,
rules of attention,
composition of games,
inspectable evidence,
navigable relationships,
and differentiated investigative behaviour.
16. Run a Real Survival Spin

This prompt is incomplete until the advanced machinery is exercised against representative project evidence.

Prefer an existing project corpus with meaningful:

revisions,
addenda,
requirements,
cross-discipline relationships,
multimodal evidence,
and known complexity.

Do not use a trivial synthetic toy if suitable real project material already exists.

Do not tune the World to known oracle answers.

Let Survival Mode investigate.

17. Show the Product Owner What Survival Mode Actually Did

At the end of the run, show the actual result.

The Product Owner should be able to see:

World

Survival Mode

Objective

What the World was trying to protect against.

Scope

What evidence was in play.

Games Played

A concise record of which games ran and why.

Example:

Change Game triggered by an addendum delta.
Propagation Game triggered by a changed operational requirement.
Convergence Game triggered because architecture and controls should reflect the changed requirement.
Missing Evidence Game triggered because downstream verification was not demonstrated.

This is an inspectable action trace, not private chain-of-thought.

Strongest Findings

The consequential things Spin discovered.

Relationship Chains

Show important project paths rather than isolated snippets.

Evidence

Allow the finding to be traced to its sources.

Uncertainty

Distinguish what is:

demonstrated,
supported,
inferred,
unresolved,
not found,
or not reliably inspectable.
Follow-On Investigations

Show where one discovery caused the Spin to play another game.

Final Survival Report

A concise PM-readable synthesis of what currently threatens successful convergence.18. Reporting Is a Projection of the World

The report matters, but it is not the whole product.

Treat the final Spin Report as one projection of the World state.

It should summarize:

what matters,
why,
evidence,
consequences,
relationships,
uncertainty,
and questions requiring human adjudication.

Avoid giant extracted-fact dumps.

Prefer consequential findings.

Where appropriate use:

Evidence → Concern → Question

Do not turn every finding into an RFI.

19. Acceptance Standard

The acceptance question is not:

“Did we implement a World class?”

It is not:

“Did we add Survival Mode to a dropdown?”

It is not:

“Did the report become longer?”

The acceptance question is:

Does ARCHIOSK now feel like it entered a purposeful project World, used smarter composable Spin-Games to investigate the evidence according to that World's objective, followed consequential discoveries intelligently, and let the Product Owner inspect what it found inside the Holodeck?

A successful result should produce moments such as:

“I did not explicitly tell it to look there, but it correctly followed the consequence.”

or:

“It understood that this change matters because several project strands depend on it.”

or:

“I can enter this finding and see the evidence and related consequences.”

That is the proof.

20. Do Not Overbuild

Do not:

build every possible World,
create a generic game engine detached from GO,
invent dozens of primitives,
redesign the entire UI,
build 3D graphics,
imitate Roblox visually,
expose private reasoning,
create fake project-health scoring,
create fixed universal maturity hierarchies,
replace River,
replace Composer,
replace existing relationship types,
hard-code Survival findings,
or proceed into a broad new programme before demonstrating this result.

Advance the minimum architecture necessary for:

Holodeck → World → Prompt-Spin-Games → Real Investigation → Inspectable Result.21. Test and Preserve Existing Governance

Use the repository's established test-lane policy.

Protect:

project isolation,
provenance,
human authority,
auditability,
RFI governance,
Spin identity/history,
multimodal evidence handling,
current accepted application behaviour.

Widen tests only where warranted by changed surfaces.

22. Final Report to Product Owner

Return:

What appeared in the Holodeck
The resulting Survival Spin Report
Tests run/results
Commit/deployment state

Then STOP.

Do not propose the next World.

Let the Product Owner enter the result and decide whether the Holodeck is becoming the world system originally intended.
```

## Exact prompt text

```text
CLAUDE-BAUHAUS-CONSTRUCTIVIST-UI-01
Scientific-Artistic Surface Recomposition for ARCHIOSK/GO
Product Owner Direction

Perform a fresh visual redesign pass on the current authenticated ARCHIOSK/GO application using Bauhaus and Constructivist design principles as the only intentional visual-art lineage for this exercise.

The goal is not historical imitation.

The goal is to discover a new scientific-artistic application language appropriate for a serious intelligent project system.

The resulting UI should feel:

analytical,
engineered,
spatial,
composed,
precise,
experimental,
contemporary,
and visually memorable.

It must still function as a serious professional tool.

1. Do Not Make a Bauhaus Costume

Do not produce:

retro Bauhaus posters,
1920s typography imitation,
circles/triangles/squares scattered decoratively,
forced red/yellow/blue colour schemes,
museum-exhibition styling,
decorative modernism,
historical pastiche.

Bauhaus is valuable here as a system of thought.

Extract principles such as:

form follows purpose,
reduction,
geometry,
proportion,
visual order,
functional typography,
modular structure,
material honesty,
clear relationship between parts and whole.

Translate those ideas into a contemporary software interface.2. Do Not Make a Constructivist Costume

Similarly, do not turn ARCHIOSK into:

Soviet poster art,
propaganda graphics,
red-and-black cliché,
diagonal shapes for decoration,
distressed typography,
revolutionary-poster imitation.

Use Constructivism as a source of spatial and compositional intelligence.

Extract principles such as:

directional force,
dynamic asymmetry,
structural tension,
layered planes,
hierarchy through composition,
strong visual vectors,
relationships between masses,
purposeful imbalance,
visual communication of action and consequence.

Translate those ideas into interaction design.

3. Scientific-Artistic Is the Target

ARCHIOSK should feel as though it sits somewhere between:

scientific instrument + architectural composition + information machine + abstract artwork

without sacrificing usability.

The interface should suggest that information has:

structure,
weight,
direction,
relationship,
hierarchy,
tension,
movement,
and consequence.

Do not treat information as generic cards stacked vertically.

Ask instead:

How can the geometry of the interface itself help communicate the structure of the project?

4. Information Should Become Composition

Use the actual information architecture as the raw material of the visual composition.

Examples:

A primary project condition may occupy stronger visual territory.

A supporting source can sit as a subordinate plane.

A change may introduce directional movement.

A relationship may be expressed through alignment, adjacency, continuation, connection or controlled tension.

An unresolved conflict may create a deliberate visual interruption.

A selected item may reorganize nearby information rather than merely receive a blue border.

A transition between project states may be visible in the spatial composition.

Do not introduce decoration where the project data itself can generate the form.5. Geometry Must Have Meaning

Use geometric structure deliberately.

Possible tools include:

strong grids,
partial grids,
asymmetrical columns,
planes,
bands,
blocks,
lines,
cuts,
offsets,
layered fields,
controlled diagonals,
intersections,
negative space.

But every geometric decision must contribute to:

hierarchy,
navigation,
grouping,
sequence,
emphasis,
relationship,
or state.

If geometry communicates nothing, remove it.

6. Use Asymmetry Intelligently

Do not default to symmetrical dashboard layouts.

Constructivist composition suggests that strong asymmetry can create:

attention,
direction,
urgency,
movement,
hierarchy.

Use asymmetry where it improves comprehension.

For example:

A critical finding does not necessarily need to sit inside the same rectangle as ordinary metadata.

A major change may disturb the normal composition appropriately.

A primary evidence object can dominate space while related evidence occupies smaller supporting planes.

Do not create chaos.

The underlying grid must remain controlled.

7. Typography Is Architecture

Treat typography as a structural element, not decoration.

Review:

scale,
mass,
weight,
alignment,
spacing,
orientation,
density.

Typography should help establish:

project identity,
current state,
hierarchy,
urgency,
evidence,
secondary information.

Use a restrained type system but allow bold scale contrast where justified.

Avoid the modern SaaS habit of making every title only slightly larger than its body copy.

Important information may deserve genuine visual authority.8. Scientific Precision

Balance the artistic composition with scientific precision.

The interface should still feel calibrated.

Use:

consistent baseline relationships,
deliberate dimensions,
clear data alignment,
exact spacing systems,
readable numeric information,
repeatable component behaviour,
strong state differentiation.

The artistic character must come from composition, not imprecision.

Think:

experimental laboratory instrument designed by an architect.

9. Colour Should Behave Like Signal

Do not begin with a conventional software palette.

Develop colour based on function.

Colour may communicate:

active attention,
difference,
conflict,
confidence,
classification,
change,
warning,
selection,
evidence state.

Prefer a restrained base field with highly intentional signals.

Explore whether a small number of strong colours used decisively can outperform many weak UI colours.

Avoid rainbow categorization.

Avoid arbitrary gradients.

If a colour has no semantic or compositional role, question why it exists.

10. Negative Space Is Active Material

Treat empty space as part of the composition.

Do not fill every gap with panels.

Use negative space to:

establish hierarchy,
isolate consequential information,
create rhythm,
separate systems,
allow a strong object to dominate,
make transitions intelligible.

Bauhaus reduction should encourage removal.

Constructivist composition should encourage intentional spatial tension.11. Break the “Card UI” Habit

Actively audit whether the current interface relies too heavily on:

rounded rectangles,
floating cards,
boxed sections,
repeated panels,
identical containers.

Do not eliminate containers where they are useful.

But investigate more architectural alternatives:

shared planes,
edge-defined zones,
alignment systems,
strips,
sectional fields,
structural lines,
layered surfaces,
open compositions.

The application should not look like every contemporary SaaS product.

12. Surface Depth

Depth may be used, but not as generic glassmorphism.

Think in terms of physical planes and constructed layers.

A plane may represent:

project context,
active evidence,
secondary evidence,
tools,
findings,
system state.

Use overlap, elevation, transparency or occlusion only where it reinforces those relationships.

The user should feel that the interface has constructed spatial logic.

13. Motion Should Express State Change

If motion is used, derive it from Constructivist ideas of direction and transformation.

Motion may communicate:

entering a context,
changing state,
revealing a relationship,
propagating a change,
shifting focus,
opening a deeper layer.

Avoid decorative bouncing, glowing or cinematic effects.

Movement should explain what changed.14. Create Visual Tension Around Consequence

Ordinary information and consequential information should not look identical.

Where a project condition matters, the composition may change through:

scale,
interruption,
directional lines,
offset,
density,
contrast,
spatial dominance.

Do not rely solely on red warning badges.

Use composition itself to communicate importance.

15. Preserve Usability

Do not sacrifice usability for artistic ambition.

Maintain:

readable text,
obvious interaction targets,
accessible contrast,
keyboard/focus behaviour,
predictable navigation,
sufficient click areas,
responsive behaviour,
visual consistency.

The user must never need art-history knowledge to operate the application.

16. Review the Current Application First

Before changing code, inspect the current UI as a whole.

Identify:

where it looks generic,
where it looks overly conventional,
where it is visually fragmented,
where hierarchy is weak,
where cards or borders dominate,
where geometry has no meaning,
where information structure could become visual structure.

Select the highest-value surfaces for recomposition.

Do not redesign every screen blindly.17. Develop a Coherent Visual Grammar

Before making many isolated fixes, establish a small working grammar.

For example, define how ARCHIOSK expresses:

primary plane,
secondary plane,
active object,
selected object,
relationship,
change,
warning,
unresolved condition,
supporting metadata,
navigation,
section transition.

These should feel related.

The result should look like one designed system.

18. Use the Existing Product Content

Do not create fake decorative sample data merely to make the design attractive.

Use real existing application content wherever possible.

The strongest proof is that the visual language improves actual:

project navigation,
evidence,
findings,
Spin,
documents,
relationships,
Composer,
project state.
19. Explore, Then Converge

You have permission to experiment locally with multiple compositions.

Do not commit the first attractive idea.

Compare alternatives.

Prefer the solution that best balances:

clarity + originality + scientific precision + architectural composition + professional credibility

Then converge on one coherent direction.20. Implementation Authority

You may make safe, reversible, repository-grounded changes to:

layout,
CSS,
component composition,
typography,
spacing,
proportions,
visual hierarchy,
state presentation,
icon placement,
responsive behaviour,
motion,
surface layering.

Do not alter project governance or application semantics merely to support the visual concept.

If a deeper behaviour change appears desirable, identify it separately rather than silently changing it.

21. Visual Acceptance Test

After implementation, review the application again and ask:

Bauhaus test

Is the interface more functional, reduced, proportioned and structurally clear?

Constructivist test

Does the composition now possess purposeful direction, hierarchy, tension and spatial intelligence?

Scientific test

Does it still feel precise, reliable and calibrated?

Artistic test

Does it now have a recognizable visual identity rather than looking like generic SaaS?

Professional test

Could a serious project team use it all day without the artistic language becoming distracting or tiring?

All five should be true.

22. Final Product Owner Report

Return:

The visual weaknesses you found
The Bauhaus principles you chose to apply
The Constructivist principles you chose to apply
The visual grammar created
The surfaces materially changed
What was removed or simplified
How project information now contributes to composition
Before/after observations
Any experiments rejected and why
Responsive/accessibility verification
Tests run
Commit/deployment state

Include screenshots or live visual evidence where the development environment supports it.

Then STOP.

The Product Owner will judge whether the application has developed the intended fresh scientific-artistic character before further visual work proceeds.
```
